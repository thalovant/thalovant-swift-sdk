# Audit

Known issues, technical debt and review decisions, each tied to the code that shows it.

## Notes

- **Default key and cache folders follow `NSHomeDirectory()`.** [`Sources/ThalovantSDK/Noise.swift`](Sources/ThalovantSDK/Noise.swift) (`.thalovant`) and [`Sources/ThalovantSDK/Inventory.swift`](Sources/ThalovantSDK/Inventory.swift) (`.cache`) fall back to it when no folder is given. That is the user's home on Linux and unsandboxed macOS, and the app's container on iOS and sandboxed macOS, so two sandboxed apps never share a key by default. An app that must share one identity's key with another program passes the folder explicitly.

## Chat apps not covered (2026-11-03)

- **What:** this SDK has no methods for the chat apps routes (`/v1/bridges`), which the Python, Node, Go and Rust SDKs and the MCP server cover. `contracts/sdk-parity.json` records `chat-apps` as not applicable.
- **Status:** a scope decision, not a defect: the API's impact records for chat apps list no obligation here. Revisit if an app built on this SDK needs to manage chat apps.

## Browser sign-in (2026-11-08, 0.12.0)

Evidence: the full `swift test` on Linux (Swift 6.3.2) and the full `swift test` in the CI's `swift:5.10` image (5.10.1). Both run `Tests/ThalovantSDKTests/BrowserLoginVectorTests.swift` (all 119 cases of `browser-login-vectors.json`, every recorded digest equal to the Python reference's at `39e31d8`) and `Tests/ThalovantSDKTests/BrowserLoginTests.swift` (the platform-neutral `BrowserLoginTests` and the macOS/Linux `BrowserLoginListenerTests`). The first round recorded a filtered 5.10 run (`--filter "BrowserLogin|DeviceLogin|NativeSignIn|VersionTests"`); this round runs the whole suite there. macOS and iOS were not built locally; hosted CI builds and tests macOS.

- **The denied and expired messages still say "device sign-in".** `browserLogin` throws the device login's own `ThalovantDeviceLoginError.denied` and `.expired` ([`BrowserLogin.swift` L788-L790](Sources/ThalovantSDK/BrowserLogin.swift#L788-L790)), as the porting brief requires: there are no new error types. Their fixed messages ([`DeviceLogin.swift` L25-L29](Sources/ThalovantSDK/DeviceLogin.swift#L25-L29)) read "The device sign-in request was denied" and "... Call loginWithBrowser() again". Changing them would change device login. A caller should branch on the case, not the text. See `SUGGESTIONS.md`.
- **`acceptDeviceToken` reads `tokenId` back after storing it (pre-existing device-login code, not changed).** [`DeviceLogin.swift` L384](Sources/ThalovantSDK/DeviceLogin.swift#L384) builds the result with `tokenId: self.tokenId`. A sign-in completing on another task between `keepSignIn` and that read could hand back the other sign-in's id. Browser sign-in no longer goes through it: `browserTokenResult` ([`BrowserLogin.swift` L852](Sources/ThalovantSDK/BrowserLogin.swift#L852)) reads the id from the same answer as the token. The device-login path is reported to the lead, not changed here.
- **Accepted connections become close-on-exec one call after `accept`.** Swift's Glibc module does not export `accept4`, so each accepted socket is made close-on-exec with `fcntl` right after `accept` ([`Loopback.swift` L501](Sources/ThalovantSDK/Loopback.swift#L501), [L726](Sources/ThalovantSDK/Loopback.swift#L726)). A child process spawned in that window could inherit one browser connection. On Linux the listening socket itself is created with `SOCK_CLOEXEC` ([L713](Sources/ThalovantSDK/Loopback.swift#L713)), so the port is never inherited. On Apple platforms every socket gets the same `fcntl` one call after it is created. Not verified on macOS here. Risk: low. The browser is opened once, right after the port is bound and before any tab connects.
- **Connections: at most 64 held, accepted 16 at a time** ([`Loopback.swift` L246-L248](Sources/ThalovantSDK/Loopback.swift#L246-L248)). The cap counts every connection held, the accepted tab waiting for its page included. Past 64, every waiting connection that has something to read is served first, so a callback that has arrived is never the one closed. Only then does the oldest connection that has not sent its head make room ([`makeRoom`, L523](Sources/ThalovantSDK/Loopback.swift#L523)), so idle sockets cannot keep the real tab out. A flood cannot starve the loop's callbacks, deadlines or closing either. The Python reference has no cap. Tested by `testAFloodOfIdleConnectionsDoesNotKeepTheTabOut`.
- **Drain before close** ([`drain`, `Loopback.swift` L622](Sources/ThalovantSDK/Loopback.swift#L622)). After every answer the write side is shut and what the browser still sends is dropped, for at most 2 s and 1 MiB, in the poll loop, so no other connection waits on it. Closing the listener closes those at once, but gives the accepted tab up to 1 s to read its page. Tested by `testAnEarlyAnswerIsNotLostToAReset` (a 600 KB head and a 600 KB unread body) and `testDrainingAConnectionIsBounded`.
- **The exchange goes out once, on a connection of its own** (`performOnce`, [`ControlPlane.swift` L602](Sources/ThalovantSDK/ControlPlane.swift#L602)). URLSession reuses a session's connections, and an HTTP stack that finds a reused connection dead can resend a request on a fresh one. Measured on the shared session, the exchange reused the configuration's connection on both Linux toolchains. On Swift 6.3.2 the dying POST was sent once and failed at once. On the CI's 5.10.1 it was sent once and then hung until the 60 s request timeout, so the tab waited a minute. The dedicated session makes the reuse impossible on every platform. `testTheExchangeIsSentOnceEvenWhenItsConnectionDies` pins one POST, on a new connection, against a real keep-alive server.
- **No request leaves the API's origin** ([`ControlPlane.swift` L513](Sources/ThalovantSDK/ControlPlane.swift#L513)). Every request is checked against the API's scheme, host and port. Paths are concatenated onto the API's address, so in Swift a path cannot move the host. The check is the contract's defence in depth, and the configuration already refuses a token endpoint with a colon.
- **A loopback listener that cannot start is an error, in `auto` too.** That is the porting brief's decision at `39e31d8` ("Decided and not changed"). A sandboxed macOS app without `com.apple.security.network.server` therefore gets an error from `interactiveLogin()`. README and FAQ say to add the entitlement or pass `method: .device`.
- **IP hosts are parsed by the SDK, not the platform** (`ipv4Value`, `ipv6Hextets` in `BrowserLogin.swift`). CI on `bf70147` failed on macOS only. macOS's `inet_pton(AF_INET)` accepts `01.2.3.4`, which glibc and the reference's `ipaddress` refuse, so `https://01.2.3.4/authorize` was usable on a Mac and not on Linux. Both address forms are now ports of Python's `ipaddress` rules (four octets with no leading zero; IPv6 hextets, `::` and an embedded IPv4). `testIPHostsAreReadAsTheReferenceReadsThem` pins 39 of the reference's own verdicts on every platform.
- **Authorization hosts follow the reference's verdicts.** Only a decimal last label counts as numeric (`https://auth.0x1/authorize` is usable, as in the reference's `_real_host`). An IPv6 zone must be non-empty, with no second `%`, as in Python's `ipaddress`. The configuration verdict decides which method `auto` picks, so it is the cross-SDK contract. The hex case is reported to the lead as a gap: a WHATWG browser reads `0x1` as a number.
- **A HEAD answer never has a body.** That includes the 400 for an oversized or unreadable head that begins with `HEAD ` ([`Loopback.swift`, `serve`](Sources/ThalovantSDK/Loopback.swift)). The reference sends a body on that path; the brief and RFC 9110 say none. Tested by `testAnOversizedHeadRequestGetsItsAnswerWithNoBody`.
- **The authorization URL is printed, state included.** The vectors' `prompt` member requires it; it is what the person opens. Errors, logs and the listener never carry the state.
- **No exclusive-address option.** The porting brief's `SO_EXCLUSIVEADDRUSE` is Windows-only, and this package does not support Windows. On Linux and macOS, another process cannot bind the same port unless both sockets set `SO_REUSEPORT`, and this one does not.
- **The scripted API is a URLProtocol, not a loopback HTTP server.** `BrowserApi` ([`BrowserLoginVectorTests.swift` L497](Tests/ThalovantSDKTests/BrowserLoginVectorTests.swift#L497)) checks every request through the SDK's real URLSession path, as this SDK runs every other vector file: method, path, the four exchange fields, the verifier's S256 against the URL's challenge (with a second, C SHA-256), and `Authorization`. The browser side is a real TCP client against the bound port ([`RawHTTP`, L655](Tests/ThalovantSDKTests/BrowserLoginVectorTests.swift#L655)). The single-send check uses a real server (`TinyHTTPServer`).
- **Secrets.** The exchange's answer is redacted before its message is built ([`redactedBody`, `BrowserLogin.swift` L866](Sources/ThalovantSDK/BrowserLogin.swift#L866)), so a message cut at 200 characters keeps no part of a secret. Every error is then rebuilt from scrubbed fields (`withoutSecrets`, [L981](Sources/ThalovantSDK/BrowserLogin.swift#L981)).
  - The scrub ([`redacting`, L908](Sources/ThalovantSDK/BrowserLogin.swift#L908)) finds every occurrence in the whole original text before replacing any, across an existing `[redacted]` too. It leaves alone only a match lying wholly inside an existing marker, which keeps it idempotent, and replaces whole a marker that a match runs into.
  - It is stricter than the reference's `_scrub` in three cases, none of which a vector reads. Two overlapping values leave nothing of either, where the reference's longest-first pass would leave the tail of the second. A secret that contains `[redacted]` is still taken out, where the reference splits at the marker first and leaves it whole. Back-to-back values become one marker, where the reference writes two.
  - Only RFC 6749's `error` codes are kept from a callback ([`loopbackOAuthErrors`, `Loopback.swift` L51](Sources/ThalovantSDK/Loopback.swift#L51)).
  - The listener logs nothing, and `LoopbackCallback`'s description hides the code.
- **A callback read after the wait's deadline does not count** ([`Loopback.swift` L570](Sources/ThalovantSDK/Loopback.swift#L570)). The same rule as the loop's own expiry (`waitIsOver`, [L417](Sources/ThalovantSDK/Loopback.swift#L417)), so a callback that arrives as the timeout passes cannot install a token after `expired`. The window is between `poll` returning and the callback being read. Only the shared rule is unit-tested; the race itself cannot be made deterministic without a fake clock.
- **Tests are gated by platform.** The listener and `browserLogin` tests compile on macOS and Linux only ([`BrowserLoginTests.swift` L398](Tests/ThalovantSDKTests/BrowserLoginTests.swift#L398)). The pure sections, the configuration rules and the chooser's device path compile everywhere, and a mobile-only test checks that `interactiveLogin` uses a device login there. No mobile test run exists in CI.
- **Swift-specific behaviour.** The printed notice is flushed (`fflush(stdout)`), so a piped CLI shows the URL at once. A timeout is clamped: negative or NaN is none, and infinity is a century. A `LoopbackListener` that was never started answers `wait` with no callback, where Python raises.
